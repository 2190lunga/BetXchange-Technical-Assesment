# Assumptions, Methodology, and Known Limitations

This document is the single source of truth for every judgment call, assumption, and
limitation behind the BetXchange KPI tables, views, and dashboard. The case study brief
explicitly requires assumptions to be clearly stated — this file is that disclosure.

It exists because an earlier version of this project produced numbers (a "risk" table,
product-level revenue, a company "net profit" figure) that could not be explained when
challenged, and in one case were mathematically impossible. Every correction made is
logged here with the evidence that justified it, so every number in the dashboard and
reports can be traced back to a specific, reproducible rule.

---

## 1. Sign convention: customer result vs. operator revenue (critical correction)

**The problem.** The original pipeline computed a single field, `net_profit = win_total -
price_total`, and then reported it everywhere (dashboard, executive notes, blueprint) as
if it were *BetXchange's* profit. This is the customer's result, not the company's. Since
a bookmaker is structurally expected to pay out less than it takes in, this field is
*expected* to be negative in aggregate — and a negative value for it is **good news for
the company**, not bad news.

**The evidence.** Querying `cleaned.transactions` directly:

| Month | `win_total − price_total` (customer result) | `price_total − win_total` (operator revenue) |
|---|---|---|
| May | −R7,357,460 | **+R7,357,460** |
| June | −R9,925,836 | **+R9,925,836** |
| July | −R16,615,944 | **+R16,615,944** |

The project's documents (`docs/powerbi-dashboard-blueprint.md`, `reports/executive_presentation_notes.md`)
previously stated "net profit remains negative in all months" and "the financial model is
under pressure" — the opposite of what the data shows once the correct perspective is used.

**The fix.** `cleaned.transactions` now has two fields:
- `customer_net_result` = `win_total − price_total` (customer's perspective; kept for
  customer-level analysis, e.g. identifying customers who are net winners).
- `operator_revenue` = `price_total − win_total` (BetXchange's gross gaming revenue; the
  correct figure for any claim about company profitability, margin, or financial health).

Every downstream table (`monthly_kpis`, `customer_kpis`, `product_kpis`, `risk_kpis`) and
view (`vw_financial_analysis`, `vw_risk_analysis`) was rebuilt around this distinction.
`operator_margin_pct = operator_revenue / total_stake * 100` is the house edge / hold.

**Residual assumption.** `paid_out` and `win_total` differ in ~2.6% of rows (7,500 of
286,244) by small-to-moderate amounts. We treat `win_total` as the customer's win amount
(used in `customer_net_result`/`operator_revenue`) and `paid_out` as a separate reported
field, carried through unchanged. We did not reconcile this discrepancy against a payment
ledger because no such source exists in this dataset; it is noted here as a data-quality
observation, not resolved as a bug.

## 2. Risk methodology (Craig)

**The problem.** The original `risk_kpis`/`vw_risk_analysis` used hardcoded thresholds
(`price_total > 5000`, `> 1000`) with no stated justification, labeled a plain count of
distinct active users as `risky_users` (it was identical to `active_customers` in
`monthly_kpis`), and called customer losses "loss events" / "loss ratio" — inheriting the
sign-inversion problem above (a customer loss is operator revenue, not an operator "loss").

**The fix — fully reproducible, computed from the data itself:**
- **`large_stake_threshold`**: the 95th percentile (`QUANTILE_CONT(price_total, 0.95)`) of
  that specific month's transaction stakes. This is a *relative*, data-derived threshold,
  not a fixed dollar figure, so it adapts as monthly volume changes (volume grew ~75% May
  to July, so a fixed threshold would silently become less meaningful over time).
- **`customer_win_event_count`**: transactions where `customer_net_result > 0`. This is
  **payout exposure for the operator** (the operator paid out more than it took on that
  bet), not a company "loss" — relabeled from the original `loss_events`.
- **`top10_user_stake_share_pct`**: the share of a month's total stake generated by its
  ten highest-staking users — a revenue-concentration/dependency measure.
- **Stake-percentile bands** (`vw_risk_analysis.stake_percentile_band`): each user-month
  is ranked via `NTILE(100)` against *all user-months in that same source_month* and
  bucketed into Normal (bottom 80%) / Elevated (80th–95th pct) / High (95th–99th pct) /
  Very high (top 1%). Percentile boundaries use strict `>` comparisons against the NTILE
  bucket number (`> 99`, `> 95`, `> 80`) so that "top 1%" means exactly the top bucket,
  not an off-by-one 2% or 6% band.

**What this methodology can prove, with evidence (July):**
- Operator margin: 5.66% of stake.
- Large-stake transactions (>R3,929, that month's 95th percentile): 5,656 transactions,
  90.9% of stake volume.
- Top 10 users: 36.3% of July's stake.
- Top 1% of users (148 people): 77.3% of July's stake.
- 11.6% of transactions were customer wins (payout exposure).

**What this methodology explicitly cannot do, and why:**
- **Cannot detect fraud, collusion, bonus abuse, or multi-accounting.** The source data
  (`cleaned.transactions`, `cleaned.users`, `cleaned.slips`) has no device ID, IP address,
  payment method, session/login metadata, or any field that links separate user accounts.
  Any claim to the contrary would be unverifiable and must not be made.
- **Cannot explain *why* a user has a large stake** (e.g. legitimate high-roller vs.
  problem gambling vs. data error) — it can only flag *that* a stake is statistically
  unusual for the month.
- Percentile-based flags are relative to each month's own distribution, so a user flagged
  "Very high" in May (a lower-volume month) might not be flagged the same in July even
  with an identical stake — this is intentional (it tracks relative concentration, not an
  absolute dollar-risk ceiling) and should be stated explicitly if compared across months.

## 3. Product-level financials (modeled, not measured)

**The problem (two compounding bugs).**
1. `cleaned.slips` retained a per-user, per-product **"Total" row** (the raw export's own
   monthly subtotal) *alongside* the per-day rows for the same user/product/month.
   Verified: `SUM(slip_count)` for `activity_day = 'Total'` (11,439,121) is nearly
   identical to `SUM(slip_count)` for all non-Total rows combined (11,435,000) — i.e. the
   Total rows duplicated activity that was already counted day-by-day.
2. The original `product_kpis` query joined `cleaned.slips` to `cleaned.transactions` on
   `user_id + source_month` only (no day-level key). Because both tables can have many
   rows per user per month, this join created a **fan-out (cross join)** within each
   user-month group before aggregating, multiplying financial totals by the row-count of
   the other table. Verified impact: reported Casino stake for July was **R1.14 trillion**
   against a real company-wide July stake of **R293 million** — an ~4,000x inflation.

**The fix.**
- `clean_slips()` now excludes rows where `activity_day` is `"Total"` (case-insensitive),
  keeping only the genuine per-day rows.
- `product_kpis` no longer joins slips to transactions row-for-row. Instead, for each
  user-month: (a) compute the user's *real* total stake/win/operator revenue from
  `cleaned.transactions` (grouped by user+month, no fan-out), and (b) compute that user's
  share of slip volume *per product* for the month. The user's real financial totals are
  then **allocated** across products in proportion to their slip-count share.
- Columns are explicitly named `est_total_stake`, `est_total_win`, `est_operator_revenue`
  to signal that these are **modeled allocations, not direct measurements** — the source
  transactions table has no product field at all, so no exact attribution is possible
  from this dataset.

**Residual, disclosed limitation.** The six products' `est_total_stake` for July sum to
~R231.9m against a real company-wide July stake of R293.3m (~21% unattributed). This gap
exists because not every user with a transaction also has a matching slip record (and
vice versa) for that month — those users' stake cannot be allocated to any product and is
simply excluded from the product breakdown. This is disclosed on the Products dashboard
page rather than silently reconciled.

## 4. Marketing / website traffic (Holly) — previously entirely missing

**The problem.** The source dataset includes three real GA4 website traffic exports
(`2 - GA/Web Traffic - May/June/July-24.csv`), but the ingestion pipeline
(`ingest_excel_to_duckdb.py`) only scanned for `.xlsx` files. These CSVs were never
ingested, so **every marketing claim previously in this project (campaign effectiveness,
acquisition quality, channel targeting) was narrative with zero supporting data.**

**The fix.** `src/ingest_marketing_traffic.py` parses the GA4 export format directly (a
semi-structured CSV with multiple stacked metric blocks, each tagged with a date range in
comment lines) and loads: daily page views, daily total users, daily events-per-session,
country-level event counts, gender split, and the top 10 landing pages by users, into
`cleaned.marketing_*` tables and `analytics.marketing_kpis`.

**Parsing assumptions:**
- Each GA4 export repeats most blocks twice: once for the target calendar month, and once
  for a trailing 31-day "previous period" comparison window GA generates by default. Only
  the block matching the target month's exact `Start date`/`End date` is kept; the
  comparison-period block is discarded.
- **June's export genuinely ends on the 29th, not the 30th** (verified directly in the raw
  file: `# Start date: 20240601` / `# End date: 20240629`). This is treated as a real
  property of the export, not assumed to be a full 30-day month — fabricating a 30th day
  of data would be worse than reporting 29 real days.
- Only the top 10 landing pages (by the export's own descending sort) are ingested, not
  the full long tail (tens of thousands of page-path rows per file) — this was a scope
  decision to keep the marketing analysis proportionate and decision-useful.

**What this data can and cannot tell you — the most important disclosure in this section:**
- **It CAN** show: website traffic volume and trend (page views, users), geographic mix of
  traffic, and the most-visited landing pages.
- **It CANNOT** show campaign effectiveness, acquisition channel ROI, or conversion
  quality by source, because **the export has no campaign, channel, or source/medium
  dimension at all.**
- **It CANNOT be linked to the betting `user_id`.** GA4 sessions are anonymous and this
  export has no login-linked identifier, so traffic cannot be joined to transactions,
  slips, or specific customers. Any "funnel: acquisition to active usage" claim made
  previously was not possible with this data and has been removed.

## 5. Demographics: age and country (critical coverage limitation)

**The problem.** `cleaned.users` has `age_band` and `country` for every registered user,
and an unused view (`vw_user_analysis`) already computed them -- but nothing in the KPI
layer or dashboard ever joined this to actual betting activity, so the case study's
explicit requirement to "segment users by age, country, and engagement profile" was not
delivered. This was found and fixed only after being directly challenged.

**The bigger problem, found while fixing the first one.** Joining `analytics.customer_kpis`
(24,142 distinct transacting customers) to `cleaned.users` on `user_id` matches only
**7,918 customers (33%)**. The remaining **16,224 transacting customers (67%) have no
row in the Users source files at all** -- the raw Users exports (May/June/July Users.xlsx)
do not cover every customer who placed a bet; they appear to be a much smaller subset
(possibly new registrations per month, or an incomplete extract) than the full
transacting base. This is itself a data-governance finding worth raising with Gracia.

**The fix.** `analytics.demographic_kpis` reports stake and operator-revenue
contribution by `age_band` and by `country`, computed **only from the 7,918 matched
customers**. Every table, chart, and sentence that uses this data states the 33%
coverage figure -- it must never be described as covering "all customers" or used to
make a claim about the full customer base.

**What the matched subset shows (disclosed as a partial-coverage finding, not a
full-population fact):**
- Stake and revenue are concentrated in the 35-44 age band: 49.3% of stake and 57.5% of
  operator revenue from this group alone, among matched customers.
- The 18-24 age band contributes under 1% of stake and revenue among matched customers.
- South Africa accounts for 97.9% of matched customers' stake, consistent with the GA4
  marketing traffic finding (~96% of website traffic is also South African).
- `engagement_status` in `vw_user_analysis` currently reads "Active" for 100% of matched
  users (zero variation) -- it is not a useful signal with the current data and should
  not be presented as a differentiator.

## 6. Retention cohort definition (Warren)

- Cohort = the calendar month of a user's `registration_date` (`cleaned.users`).
- A cohort member is "retained" in a given activity month if they have at least one row
  in `cleaned.transactions` for that month (slip activity is tracked separately as
  `customers_with_slips` but retention_rate uses transactions only).
- This is a standard, commonly understood retention definition and was not changed in
  this revision — it was not implicated in the sign-inversion or fan-out bugs.

## 7. Other data-cleaning assumptions (unchanged from the original project, restated here for completeness)

- **Country normalisation** (`data_cleaning.py::normalize_country`): raw country strings
  are lower-cased, accents stripped, and mapped via an explicit lookup table (e.g. `"sa"`,
  `"za"`, `"s a"` → `"South Africa"`). Any value not in the lookup is title-cased as-is.
  Unmapped or blank values become `"Unknown"`. This is a best-effort normalisation, not a
  validated ISO country mapping.
- **Age banding**: `<18`, `18-24`, `25-34`, `35-44`, `45-54`, `55-64`, `65+`, else
  `"Unknown"`.
- **Duplicate users**: `cleaned.users` drops duplicate `user_id` rows
  (`drop_duplicates(subset=["user_id"])`), keeping the first occurrence encountered during
  cleaning. If a user's profile genuinely changed between files, the earliest-loaded
  version wins; this was not changed in this revision.
- **Transaction "Total" rows**: rows where `user_id`, `resolve_time_day`, or `source_month`
  contains the text "total" are excluded as export subtotal rows, consistent with the slip
  cleaning fix above.

## 8. Column rename map (old name → new name, and why)

| Old name | New name | Reason |
|---|---|---|
| `net_profit` (transactions, monthly_kpis, vw_financial_analysis) | `customer_net_result` | Was being reported as company profit; it is the customer's result. |
| *(none existed)* | `operator_revenue` | New field: the company's actual gross gaming revenue (`price_total − win_total`). |
| `engagement_score` (customer_kpis) | `net_margin_pct` | It was a profitability margin ratio, not a measure of usage frequency/engagement. |
| `risky_users` (risk_kpis) | *(removed)* | Was identical to `active_customers`; not a risk signal at all. |
| `high_value_transactions` / `avg_risk_score` (risk_kpis) | `large_stake_transaction_count` / `large_stake_share_pct` | Threshold is now the month's own 95th percentile, not a fixed, unexplained 5000. |
| `loss_events` / `loss_ratio` (risk_kpis) | `customer_win_event_count` / `customer_win_event_share_pct` | These counted customer wins, which are payout exposure for the operator, not operator "losses". |
| `stake_risk_band` (vw_risk_analysis, fixed $1,000/$5,000 bands) | `stake_percentile_band` (relative, per-month percentile) | Fixed dollar bands don't adjust for ~75% volume growth across the period and had no stated justification. |
| `profitability_flag` ("Loss exposure"/"Stable") | `customer_result_flag` ("Customer net win (payout exposure)" / "Customer net loss (revenue for operator)") | Original labeling inverted which party the flag described. |
| `total_stake`/`total_win`/`net_profit` (product_kpis) | `est_total_stake`/`est_total_win`/`est_operator_revenue` | Values are modeled allocations, not measurements; `est_` prefix makes this unavoidable to miss. |

## 9. How to reproduce every number in this project

```
python -m src.create_duckdb_database
python -m src.ingest_excel_to_duckdb
python -m src.ingest_marketing_traffic
python -m src.data_cleaning
python -m src.create_analytical_views
python -m src.generate_kpis
python -m src.export_csv_exports
```

Every figure in the dashboard and reports should trace back to a file in `output/`
produced by this exact pipeline. If a number in the dashboard or a report cannot be found
in `output/*.csv`, it is either an explicitly-labeled business judgment call (e.g. growth
priority ratings) or it is a bug — treat it as unverified until traced back to a query.
